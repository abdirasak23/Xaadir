# Xaadir Admin

A compact, responsive company HR panel and developer company-registration panel built with Next.js App Router, TypeScript, Tailwind CSS, Supabase and standalone Supabase Edge Functions. The HR scope covers staff, branch setup, QR check-in, attendance, leave, sick days, and holidays.

## Requirements

- Node.js 20+
- A Supabase project
- Supabase CLI (for CLI-based Edge Function deployment)

## Setup

1. Create a Supabase project.
2. In the Supabase SQL Editor, run [`supabase/schema.sql`](./supabase/schema.sql). It creates the company/HR membership tables and adds company ownership columns to branches and staff.
   - If you already have branches or staff from the earlier single-company panel, first register the company in the developer panel, copy its UUID from the `companies` table, verify which legacy rows belong to it, then associate those rows:

     ```sql
     update public.branches set company_id = '<company-uuid>' where company_id is null;
     update public.staff set company_id = '<company-uuid>' where company_id is null;
     ```

     Only run those updates if every unassigned legacy row belongs to that company.
3. Copy `.env.example` to `.env.local` and set:
   - `ADMIN_USERNAME`
   - `ADMIN_PASSWORD_HASH`
   - `ADMIN_SESSION_SECRET` (at least 32 characters)
   - `NEXT_PUBLIC_SUPABASE_URL`
   - `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   - `SUPABASE_SERVICE_ROLE_KEY` (server only; never use a `NEXT_PUBLIC_` prefix)
   - `EDGE_FUNCTION_SECRET`
   - `QR_SIGNING_SECRET` (at least 32 random characters)
4. Configure your developer-admin username and password:

   ```powershell
   npm run setup-admin
   ```

   This creates `.env.local`, hashes your chosen password, and generates `ADMIN_SESSION_SECRET` automatically. Keep `.env.local` private; it is ignored by git. Restart the Next.js server after changing environment settings. The generated `EDGE_FUNCTION_SECRET` and `QR_SIGNING_SECRET` are printed so they can be added to the Supabase Dashboard.
5. In **Supabase Dashboard → Edge Functions → Secrets**, set `EDGE_FUNCTION_SECRET` and `QR_SIGNING_SECRET` to the values generated by `npm run setup-admin`. These are runtime secrets used by deployed functions; deploy or paste the current `create-company`, `create-staff`, `invite-staff`, `manual-attendance`, `qr-token`, and `checkin` function code in the Dashboard. No CLI deployment is required.
6. Install dependencies and run the app:

   ```powershell
   npm install
   npm run dev
   ```

   Open `http://localhost:3000`. The admin cookie is `Secure` in production and works over local HTTP for development.
7. Sign in to `/admin-panel/login` with the developer-admin username/password. Register a company and its HR contact. Share the one-time HR login details shown after creation.
8. The HR contact signs in at `/login` using their email and the temporary password (`Xd` + the last four phone digits), changes the password, then creates the company's branches and staff.

## Deploying the admin login on Render

Render does not read your local `.env.local` file. In the Render service, open **Environment** and add these server-only variables:

- `ADMIN_USERNAME`: the developer-admin username you want to use.
- `ADMIN_PASSWORD_HASH`: generate a bcrypt hash locally with `npm run hash-password`, then paste the printed hash as the value. Do not use the plain password here.
- `ADMIN_SESSION_SECRET`: a private random value of at least 32 characters. Generate one locally with `node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))"`.
- `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `EDGE_FUNCTION_SECRET`, and `QR_SIGNING_SECRET` for the app's other features.

Save the environment changes and redeploy the Render service. Never add the admin password or service-role key to a `NEXT_PUBLIC_` variable, commit them, or share them in chat. `npm run setup-admin` creates a local `.env.local`; it does not configure Render.

## Deploying to Cloudflare Workers

This repository uses `@opennextjs/cloudflare` to adapt the existing Next.js app to Workers. Local development remains `npm run dev`. In **Workers & Pages → xaadir → Settings → Builds**, configure:

- Build command: `npx @opennextjs/cloudflare build`
- Deploy command: `npx @opennextjs/cloudflare deploy`
- Preview command: `npx @opennextjs/cloudflare preview`

Add the application variables to both Workers Builds **Build variables and secrets** and the Worker’s runtime **Variables and Secrets**. Use plain variables for `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, and `ADMIN_USERNAME`. Use encrypted secrets for `ADMIN_PASSWORD_HASH`, `ADMIN_SESSION_SECRET`, `SUPABASE_SERVICE_ROLE_KEY`, `EDGE_FUNCTION_SECRET`, and `QR_SIGNING_SECRET`. The public Supabase URL/key are inlined during Next.js compilation; all private values must remain server-side. Never commit `.env.local` or `.dev.vars`.

The Worker is named `xaadir`; `wrangler.jsonc` configures its OpenNext entry point, static assets, `nodejs_compat`, and deployment-safe `keep_vars`. Next Image optimization is disabled so existing local and remote images render without requiring a paid Cloudflare Images binding. The static images still use Cloudflare’s asset delivery.

## Leave, sick days, and holidays

1. Run [`supabase/leave.sql`](./supabase/leave.sql) in the Supabase SQL Editor after `schema.sql`. It enables RLS on the new tables, grants access only to `service_role`, and adds attendance statuses and the annual leave allowance field.
2. Deploy or paste these five standalone functions from the Supabase Dashboard: `leave-save`, `leave-cancel`, `holiday-save`, `holiday-delete`, and `attendance-convert`. Redeploy/paste the updated `checkin` function so it enforces leave and holiday blocks. Set `EDGE_FUNCTION_SECRET` on the Supabase project to the same value used by the Next.js server. The admin functions verify `x-admin-secret` and use the service role only on the server.
3. Open **Leave** in the HR sidebar. Add company-wide or branch holidays, including the confirmed dates for Eid, 26 June, and 1 July for the relevant year. The quick-add field accepts one `YYYY-MM-DD, Name` entry per line.
4. To verify leave entry, add three weekdays of sick leave for a test staff member. Confirm that sick attendance entries appear and Friday is skipped.
5. Check the attendance percentage by hand: for 20 eligible workdays, 3 sick days, and 14 present days, it should be `14 / (20 - 3) = 82%`.
6. Scan a QR code on a leave day and confirm that the check-in function returns HTTP 403 with `ON_LEAVE`. Cancel the request, then confirm check-in is available again.
7. Convert a past absent day to sick leave from the attendance detail, and confirm the status and percentage update. Add a holiday and confirm active staff in its scope receive holiday entries, while existing check-ins remain untouched.

## Split shifts and payroll

1. Run [`supabase/payroll.sql`](./supabase/payroll.sql) in the Supabase SQL Editor after `schema.sql` and `leave.sql`. It migrates existing staff to their current single shift, adds salary and schedule fields, changes attendance to one row per staff shift, and sets the lateness grace period to five minutes.
2. Redeploy the updated `create-staff`, `checkin`, `manual-attendance`, `leave-save`, `holiday-save`, and `attendance-convert` Edge Functions. A staff member can now have up to eight ordered, non-overlapping daily shifts. Each successful QR scan checks out the open shift; the next scan starts the next scheduled shift.
3. In **Staff**, set the monthly salary and add each daily shift, such as 08:00–12:00 and 15:00–21:00. Existing schedules are migrated automatically as one shift.
4. Open **Payroll**, select the month and staff member, review the attendance and deduction ledger, then download the individual monthly statement as PDF or Excel. Lateness is recalculated from the actual check-in against the corresponding shift and starts after five minutes.

Payroll uses the configured monthly salary, scheduled workdays (excluding Fridays and applicable branch holidays), the sum of the staff member's shift hours, and unexcused absences on past scheduled workdays. The current day and approved leave are not counted as absences. Salary amounts are displayed without a currency symbol because this workspace does not store a payroll currency setting.

Weekend and date rules are centralized in [`shared/attendance-rules.ts`](./shared/attendance-rules.ts): Friday is the weekend day, and dates are interpreted in `Africa/Mogadishu`.

## Security notes

- The Supabase service-role key is used only from server code and Edge Functions. All admin database endpoints are protected by the signed, HTTP-only admin cookie.
- Developer-admin credentials are environment-based and bcrypt verified. Company HR accounts use Supabase Auth and are linked to a company membership. Their first sign-in requires a password change.
- All HR API queries are scoped to the signed-in company. Company ownership is recorded on branches and staff; attendance is scoped through its staff member.
- Database tables have RLS enabled and no client-access policies. Only service-role code accesses the tables.
- Admin Edge Functions require `x-admin-secret`. The public `qr-token` endpoint requires the branch's high-entropy live key; the standalone wall display URL uses that same key.
- Static QR codes contain the permanent branch secret. Treat printed codes and live display URLs as sensitive access material.
- The initial staff password is `Xd` followed by the phone number's last four digits. Staff password changes are flagged for later enforcement by the Flutter app; this admin panel does not implement the staff app.
- The developer control panel is at `/admin-panel/login`; company HR sign-in is at `/login`. Company creation runs in the server-only `create-company` Edge Function; its one-time temporary password is never stored in the company database.

## Attendance calculation

QR and manual records use the staff member's branch, shift start, and grace period. A check-in later than `shift_start + grace_minutes` is marked late; `late_minutes` is the number of minutes beyond the grace period. Manual records use the same attendance table and are identified by `source = 'manual'` and `created_by = 'admin'`.
